# Contributing to Pinwall

Thank you for wanting to change Pinwall. This page is what you need to build it, test it and send
a change. To report a security problem, do not open an issue: follow [SECURITY.md](SECURITY.md).

## Set up

Pinwall is a TypeScript monorepo that uses pnpm workspaces: the server (`apps/server`, Node.js and
Hono), the web app (`apps/web`, React and Vite), shared code and the page annotator (`packages/`),
the release tooling (`tools/`) and the end-to-end suites (`e2e/`).

You need Node.js 24, and Docker for the integration and acceptance tests. pnpm comes with Node
through corepack:

```sh
corepack enable
pnpm install
```

## Check your change

Run what fits the change while you work, and run the first three before you send it:

```sh
pnpm lint          # Biome: formatting and lint rules
pnpm typecheck     # TypeScript, strict, for every package and the end-to-end suites
pnpm test          # unit tests of every package, with Vitest
```

`pnpm format` fixes what Biome can fix. The heavier suites:

```sh
pnpm test:integration   # starts PostgreSQL and an S3-compatible store with Docker, then runs pnpm test against them
pnpm test:e2e           # Playwright, in a browser, against a real server; run `pnpm exec playwright install chromium` once
pnpm test:acceptance    # builds the image and checks the acceptance list of the design, end to end
```

Write the test first, watch it fail for the reason you expect, then make it pass. A test should
check what the code does, not what a mock returns. A change to the Helm chart needs
`pnpm chart:check`, which uses `helm` and `kubeconform`.

## Configuration changes

Every setting is an environment variable, described once in `apps/server/src/config/catalog.ts`.
`docs/configuration.md` is generated from that catalog, so after you add, change or remove a setting,
regenerate it and commit the result:

```sh
pnpm docs:config
```

A test fails when the catalog, the code that reads the settings and the generated page disagree.
Another test checks the links, the anchors and every `PINWALL_` name in the documents, so use real
setting names when you write about them.

## Commits

Use [Conventional Commits](https://www.conventionalcommits.org/): a type, an optional scope and a
short summary in the imperative, such as `fix(server): refuse anchor pages with dot segments` or
`docs: explain content domains`. Keep a commit to one change that builds and passes its tests, and
say why in the body when the reason is not obvious. A change that users will notice also gets a line
in `CHANGELOG.md`.

## Original work only

Write your own code, tests, documentation and text. Do not copy from another project, whether it is
a repository, a gist or a blog, and not even lightly edited, because Pinwall can only be offered
under its license when everything in it is the contributors' own work. Learn from standards and from
the documentation of the libraries you use, then write it yourself. Using a library through its
public API is fine.

## Licenses of dependencies

Pinwall is licensed under the Apache License 2.0, and what ships in the image has to be compatible
with it. `pnpm licenses:check` reads which packages end up in the server bundle, the web app, the
annotator and the image's `node_modules`, and fails for any package whose license is not one of:

`MIT`, `ISC`, `BSD-2-Clause`, `BSD-3-Clause`, `Apache-2.0`, `0BSD`, `BlueOak-1.0.0`, `CC0-1.0`,
`Unlicense`, `Unicode-3.0`, `Unicode-DFS-2016`, `Python-2.0` and `PSF-2.0`.

A package that only builds or tests Pinwall may also use `MPL-2.0`. GPL, LGPL, AGPL, SSPL, BUSL and
packages without a license are not accepted. Check a dependency's license before you add it. A
package outside the list can come in only through an entry, with a reason, in
`tools/license-exceptions.json`, which a maintainer has to agree to. The `THIRD_PARTY_NOTICES` file
that ships with the image and with each release is generated by `pnpm licenses:notices`.
