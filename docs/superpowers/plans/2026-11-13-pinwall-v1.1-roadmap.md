# Pinwall v1.1 (personal spaces) Implementation Plan — Roadmap

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Pinwall 1.1.0:
- each person gets a private space;
- project owners can add other users as editors or viewers;
- the operator controls who may expose content outside Pinwall;
- quotas, rate limits and admin moderation make open sign-up safe.

An installation that does not opt in keeps behaving exactly like 1.0.

**Architecture:**
- **Ownership.** A project gets an owner and optional members.
- **Scope.** Every content-domain function that finds or lists content takes a `Scope`, so the
  TypeScript compiler finds every caller that must say whose view it is.
- **The predicate.** `team` mode passes everything through. `personal` mode adds one SQL predicate
  ("the viewer owns the project or is a member of it"), plus a role check for changes.
- **Defense in depth.** Content grants, live streams and publish commits check the predicate again
  at use.
- **Moderation.** Exposure approval, quotas, rate limits and admin moderation sit on top of the same
  predicate and the existing revoke machinery.

**Tech Stack:** unchanged from 1.0. Read the roadmap `2026-11-10-pinwall-roadmap.md`. No new
dependency is expected; if one is needed, it must pass the 1.0 license rules.

**Spec:** `docs/superpowers/specs/2026-11-13-pinwall-personal-spaces-design.md`, which builds on
`docs/superpowers/specs/2026-11-10-pinwall-design.md`. Read both.

**Decisions:** settled by the owner on 2026-11-13, as listed in spec §12.
- D1-A: private, with moderation.
- D2-A: CLI transfer.
- D3-B: project members.
  - Roles are editor and viewer.
  - Members are added by the email of an existing user.
  - Only the owner manages them.
- D4-A: approval through a DB switch.
- D5: 500 MB, 200 artifacts, 2 h preview.
- D6-A: `team` stays the default.
- D7: 1.1.0.
- D8-A: abuse contact and self-service deletion.

**How this plan is organized:** as for 1.0.
- This roadmap fixes the shared names, configuration, data model, routes, the access inventory and
  the milestones.
- Each milestone gets a task-level plan, `docs/superpowers/plans/2026-11-13-pinwall-mN-<name>.md`.
  An Opus planner writes it against the real code, following `.superpowers/sdd/planner-common.md`,
  once the milestones it depends on are merged.
- A milestone plan may refine anything here. If it changes a shared name, it updates this file in
  the same commit.

## Global Constraints

- **Everything in the 1.0 roadmap's Global Constraints still applies**, word for word. In
  particular:
  - original work only;
  - license rules;
  - Conventional Commits with the `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`
    trailer;
  - English UI through i18n;
  - `Cache-Control: no-transform` on content;
  - browser errors as HTML pages.
- **`PINWALL_VISIBILITY` defaults to `team`.** With the default, every 1.0 test passes unchanged,
  and every API response, MCP result and event has the 1.0 shape and content. New DTO fields are
  additive only, and are sent only in `personal` mode or when their setting is not at its default;
  absent means the 1.0 behavior. (1.0 tests compare whole bodies, for example
  `test/api/config.test.ts:30`, `test/api/artifacts.test.ts:76` and
  `test/mcp/tools-library.test.ts:98`.)
- **An id from another space answers exactly like a missing id:** `404 not_found` on REST, the same
  MCP error text, and the same HTML page. Never 403. The visibility predicate goes inside the lookup
  query, never as "fetch, then compare owner".
  - A role that sees but may not change gets `403 forbidden` for the change. Seeing is already
    allowed, so this leaks nothing.
- **`SYSTEM_SCOPE`** (unscoped access) may be imported only by an allow-list:
  - share-link resolution (`domain/share-access.ts`), guest comments (the guest branch of
    `domain/comments.ts`) and the share viewer (`api/share-public.ts`), all bound to the link;
  - search-index maintenance (`domain/search.ts`);
  - deletion and blob GC;
  - backup and restore;
  - transfer and purge;
  - the admin moderation routes;
  - startup.

  `apps/server/test/spaces/scope-guard.test.ts` enforces the allow-list.
- **No admin route moves content between spaces.** Transfer is the CLI `pinwall transfer` only.
- **The IDOR suite runs in both modes in CI,** with owner, editor, viewer and stranger cases. It is
  the release gate.
- **Run at most 2 implementer agents at once**, with `VITEST_MAX_WORKERS=2` on full runs.
- **Work happens on branch `v1.1`**, cut from `main` at the commit that adds this roadmap, with git
  worktrees for parallel milestones. Nothing is pushed or released until the owner says so.
- **Nothing on the homelab cluster changes from this work** until the rollout step in M14. Even then
  the Pinwall session first messages the homelab session (`k8s-homelab-9e`), which owns
  `infra/argocd/apps/pinwall.yaml` and the Zitadel config.

## Review Focus

These are the failure modes the spec implies but no acceptance item names. Each has its test in the
milestone that owns it.

1. **Search crowding.** Person A has 1,200 artifacts that match "report" and person B has one.
   - **Expected:** B's search returns B's one artifact on the first page.
   - **Expected:** A's matches neither push B's out of the 1,000-hit window nor change B's ranking.
   - **Owner:** M10 (filter inside `searchQuery`).
2. **Losing sight while the artifact is open.** Covers both a transfer and a removal from a project.
   - **Expected:** the person's live stream closes within one `SSE_HEARTBEAT_MS` (25 000 ms).
   - **Expected:** their review grant answers 410 on the next request, and Recent no longer lists the
     artifact.
   - **Owner:** M11 (removal) and M12 (transfer), on M10's checks.
3. **Two publishes at the quota edge at the same time,** for example an owner and their editor in
   the same space. Each fits alone; together they go over.
   - **Expected:** exactly one commits. The other gets `quota_exceeded` and leaves no version and no
     orphaned blob.
   - **Owner:** M12 (quota check under `lockUser` of the space owner, in the commit transaction).
4. **A list cursor or upload URL made before a mode switch, a transfer or a removal.**
   - A paging cursor minted in `team` mode, used after a restart in `personal` mode, returns only
     visible items.
   - An upload URL minted by an editor who was then removed is refused at commit, with no version.
   - **Owner:** M10 (cursor, commit re-check).
5. **One email belongs to several accounts.** On the owner's instance, the local Owner and the OIDC
   account may share an email.
   - **Expected:** `pinwall transfer --to <email>` refuses, lists the matching user ids, and moves
     nothing.
   - **Expected:** adding a member by that email offers the matching accounts by name and sign-in
     method, and adds only the one picked.
   - **Owner:** M12 (CLI) and M11 (members).

## Shared names (new in 1.1)

**`Config`:**
- `visibility: 'team' | 'personal'`
- `shareLinks: 'members' | 'approved'`
- `quota: { bytes: number; artifacts: number }`, where `0` means no limit
- `abuseContact: string | null`
- `termsUrl: string | null`
- `privacyUrl: string | null`

These are read in `config/load.ts` and described in `config/catalog.ts`. The catalog gets a new
section `spaces` with the title "Spaces and sharing". The quota variables go in `limits`.

**`apps/server/src/domain/spaces.ts`** (M10):

```ts

export type ViewerScope = { kind: 'viewer'; user: UserRow; visibility: Visibility; admin: boolean };
export type Scope = ViewerScope | { kind: 'system' };
export const SYSTEM_SCOPE: Scope;
export function scopeOf(c: Context<AppEnv>): ViewerScope;                // from authOf(c) + config
export function scopeForUser(deps: AppDeps, user: UserRow): ViewerScope;  // upload URLs, MCP, SSE
/** Team mode or SYSTEM_SCOPE: no predicate, every role 'owner', the 1.0 rules. */
export function seesAll(scope: Scope): boolean;
/** "Owner or member" as two IN subqueries on the project id column (no join); null when seesAll. */
export function visibleCondition(scope: Scope, projectIdColumn: string): RawBuilder<SqlBool> | null;
export function whereVisible<QB>(qb: QB, scope: Scope, projectIdColumn: string): QB;   // qb when seesAll
/** The viewer's role on a project they can see; 'owner' for everyone in team mode and system, without a query. */
export async function roleIn(db: Db, scope: Scope, projectId: string): Promise<ProjectRole>;
export async function rolesIn(db: Db, scope: Scope, projectIds: readonly string[]): Promise<Map<string, ProjectRole>>;
export function can(role: ProjectRole, action: SpaceAction, ctx?: { publishedBy?: string | null; userId?: string }): boolean;
export type SpaceAction =
  | 'comment' | 'publish' | 'editArtifact' | 'deleteArtifact' | 'deleteOthersComment'
  | 'createShareLink' | 'revokeShareLink' | 'manageProject' | 'manageMembers';
export function forbiddenRole(action: SpaceAction): AppError;   // 403 forbidden, details.reason 'role'
/** Personal mode: forbiddenRole unless can(); seesAll: returns, and the module's 1.0 rule applies. */
export function assertCan(scope: Scope, role: ProjectRole, action: SpaceAction, ctx?: { publishedBy?: string | null; userId?: string }): void;
export async function teamDefaultProject(db: Db): Promise<ProjectRow | undefined>;   // the oldest is_default = 1 project
/** Team/system: the team default. Personal: the viewer's own; else adopts an unowned default holding no artifact; else creates one. */
export async function defaultProjectFor(deps: AppDeps, scope: Scope): Promise<ProjectRow>;
// M11: membership changes and role checks take turns on Postgres (personal mode; nothing on SQLite)
export async function lockProject(trx: Transaction<Database>, dialect: DbDialect, projectId: string): Promise<void>;   // FOR UPDATE: a membership change
export async function holdProject(trx: Transaction<Database>, dialect: DbDialect, visibility: Visibility, projectId: string): Promise<void>;   // FOR SHARE, any scope
/** roleIn for a write in its transaction: holdProject, then the role in a later statement. */
export async function holdRoleIn(trx: Transaction<Database>, dialect: DbDialect, scope: Scope, projectId: string): Promise<ProjectRole>;
```

`apps/server/src/domain/spaces-startup.ts` (M10) holds `readSetting`, `writeSetting`,
`checkVisibility`, `confirmTeamVisibility` and `startSpaces`.

`can` encodes the table in spec §4.3:
- Editors may change or delete only what they published (`publishedBy === userId`).
- In `team` mode `roleIn` returns `'owner'`, but the 1.0 rules still apply through the existing
  `canDelete`, `canDeleteComment` and `canRevoke`, which take the `Scope`.

**Domain signatures** (M10, refined by the M10 plan against the code). Every content function
says whose view it serves, in one of two ways. Callers in `api/`, `mcp/` and
`content/raw-links.ts` pass `scopeOf(c)` or `scopeForUser(...)`.
- **It gains `scope: Scope`** after `deps` or `db` (after `trx, dialect` for the hold and lock
  helpers) when it has no acting user: `getArtifact`, `holdArtifact`, `lockArtifact`,
  `listArtifacts`, `listRecent` (`ViewerScope`), `getProject`, `listProjects`, `updateProject`,
  `updateArtifact`, `listVersions`, `checkTarget`, `listThreads`, `getThread`, `getComment`,
  `listShareLinks`, `diffVersionFiles`, `diffTextFile`, `diffMarkdownFile`, `toArtifactSummary`.
- **It keeps its signature and derives `scopeForUser(deps, actor)`** when it already takes the
  acting person: `createProject`, `commitVersion`, `restoreVersion`, `deleteArtifact`,
  `deleteVersion`, `createThread`, `addReply`, `editComment`, `deleteComment`, `resolveThread`,
  `reopenThread`, `createShareLink`, `revokeShareLink`, the ingest functions and
  `createPublishSession`. A guest comment acts under `SYSTEM_SCOPE`, bound to its link.
- **Unchanged:** functions handed a row found through a scoped lookup (`getVersionByNumber`,
  `getCurrentVersion`, `versionOf`, `listVersionFiles`, the counts).

**`searchQuery(h, q, limit, scope)`** (`h` is `{ db, dialect }`): with `seesAll(scope)` it runs
the 1.0 SQL; otherwise it joins `artifacts` and applies the predicate before `LIMIT`. Both the
SQLite FTS5 query and the Postgres `tsvector` query do this.

**Members** (M11), in `domain/members.ts` (refined by the M11 plan):
- `listMembers(deps, scope, projectId): Promise<ProjectMember[]>`
- `findUsersByEmail(db, email): Promise<UserRow[]>`: active users with that email, ignoring letter
  case; OIDC accounts only with a verified email.
- `addMember(deps, scope, projectId, { email, role, userId })`: the owner only; the lookup runs
  after the role check.
- `setMemberRole(deps, scope, projectId, userId, role)`: from editor to viewer it revokes the
  person's links on the project's artifacts.
- `removeMember(deps, scope, projectId, userId)`, which a member can also use on themselves to
  leave.
- `endProjectAccess(trx, projectId, userId, now): Promise<EndedAccess>`, in the change's
  transaction, which holds the project with `lockProject`. It revokes the person's links on the
  project's artifacts and ends their grants there. `finishEndedAccess(deps, ended)` runs after
  commit: it ends those links' streams, re-checks the person's member streams
  (`recheckViewerStreams`) and drops their upload URLs into the project
  (`revokeUploadSessionsFor`).
- Building blocks M12 reuses: `revokeProjectGrants` (`content/grants.ts`),
  `revokeProjectShareLinksOf` (`domain/shares.ts`), and `VIEWER_ACCESS_TOPIC` with
  `recheckViewerStreams` (`domain/live.ts`).

**DTOs** (`@pinwall/shared`; additive only):
- `ArtifactSummary.can_manage: boolean`, computed on the server. It replaces the SPA's
  `admin || created_by === me` rule.
- `Project.owner: { id, name } | null` and `Project.role: 'owner' | 'editor' | 'viewer'`.
- `ProjectMember { user: { id, name, email | null }, role, added_at }`. `email` is set only for the
  owner's view. The member list leaves out the owner, who is `Project.owner`.
- `MemberCandidate { user_id, name, kind: 'owner' | 'oidc' }`, plus `AddMemberRequest`,
  `UpdateMemberRequest` and `ProjectMemberList` (M11).
- `PublicConfig.visibility`, `PublicConfig.share_links`, and `PublicConfig.abuse_contact`,
  `terms_url`, `privacy_url`.
- `Me.can_create_share_links`, `Me.usage: { bytes, artifacts }` and `Me.limits: { bytes: number |
  null; artifacts: number | null }`.
- Admin DTOs: see Routes.

**Errors:**
- A new `ErrorCode` `quota_exceeded` (HTTP 413). Its `details` are `{ used_bytes, limit_bytes,
  needed_bytes, space_owner }` or `{ used_artifacts, limit_artifacts, space_owner }`.
- Refusing a link because of policy uses `forbidden` with `details.reason =
  'share_links_not_approved'`.
- A role refusal uses `forbidden` with `details.reason = 'role'`.
- Moving an artifact to a visible project of another owner uses `forbidden` with
  `details.reason = 'other_space'`.
- Adding a member (M11):
  - several matching accounts give `conflict` with `details.reason = 'several_accounts'` and
    `details.candidates`;
  - an existing member gives `conflict` with `details.reason = 'already_member'`;
  - no account gives `not_found` with `details.field = 'email'`;
  - adding oneself gives `bad_request` with `details.field = 'email'`.

**Rate rules** (`RATE_RULES`, keyed by user id):
- `publish`: 60 per 600 000 ms. It replaces `PUBLISH_SESSION_RATE` and counts sessions, inline
  publishes, web uploads and restores.
- `grant`: 600 per 3 600 000 ms.
- `shareLinkCreate`: 30 per 3 600 000 ms.
- `projectCreate`: 30 per 3 600 000 ms.
- `memberLookup`: 30 per 3 600 000 ms, which counts every add-by-email.

**CLI** (`main.ts`):
- `pinwall transfer --from <id|email> --to <id|email>`
- `pinwall visibility team --confirm`

### M10 Spaces core (spec §3, §4, §5, §8.1)
